## THE OPEN PROBLEM — read this first

The confidence ladder ran on GitHub tonight and promoted NOTHING.

    live events   : 130
    status        : { reported: 130 }
    checked by GDELT : 0
    expired       : 0

That is not a finding about the events. It is a plumbing failure.

The 'Confidence ladder' step took **25 minutes 26 seconds**. At the
configured 1.4s gap, 130 queries should take about 3 minutes. 25 minutes is
130 queries each hitting the 20-second AbortController timeout. GDELT was
effectively unreachable from the GitHub runner for the whole run.

This is the SECOND time GDELT has failed specifically from GitHub Actions.
The first was GEO 2.0 (dead everywhere, 404). This is DOC 2.0, which DOES
work from a browser and DID work from a runner in an earlier probe — but not
with the query shape the ladder uses.

Suspects, in the order worth testing:
  1. the startdatetime / enddatetime parameters
  2. the quoted `query="Belgorod"` form
  3. GDELT rate-limiting after N rapid queries from one IP
Test each with plain curl in a throwaway workflow before touching the ladder.

## What went RIGHT and must not be undone

The safety guards worked on their first real test. GDELT errored on every
query, so `gdeltErrors > 0`, so expiry was SKIPPED entirely and no event was
touched. Without that guard the run would have expired 99 of 130 events —
events that had never been checked — and there was no expired-events.json at
that point to recover them from.

Do not weaken these:
  - confidence-ladder.mjs defaults to a DRY RUN; --write is required
  - expiry needs BOTH: post older than 14 days AND a `checkedOn` stamp
  - if the GDELT pass has any errors, expiry is skipped for that run

## The finding that matters most

reported by two of them. Every "corroboration" in the data was a channel
citing itself — 22 such entries, all stripped.

for a tool meant to be cited, and the answer is more independent sources —
